# 작업 실행 안정성과 Dispatch 대기 개선 실행계획

기준은 로컬 `develop`의 `033a8ee`다. 먼저 취소하거나 시간 초과된 tmux 작업의 실제 실행 상태를 바로잡고, 한 작업의 오류가 큐 전체를 막는 범위를 줄인다. Dispatch 대기 개선은 별도 PR로 바로 진행할 수 있다. 유휴 폴링 최적화는 실측 후 결정한다. 이전 네 가지 개선의 완료 내역은 [v0.1.4 릴리스 노트](release-notes-v0.1.4.md)에 있다.

| 우선순위 | 작업 단위 | 예상 비용 | 착수 순서 |
|---|---|---|---|
| 1 | 시작 후 저장되지 않은 tmux 세션 회수 | 중간 | 첫 번째 브리지 PR |
| 2 | 실행 중인 tmux 작업별 수집 오류 격리 | 낮음 | 1번 이후 같은 러너에서 작업 |
| 3 | 시간 초과 시 tmux 세션 종료 확인 | 낮음~중간 | 2번 위에서 재시도와 슬롯 점유를 함께 검증 |
| 4 | Dispatch 대기에서 저장된 알림 우선 조회 | 낮음 | 1~3번과 독립적이며 병렬 진행 가능 |
| 5 | 유휴 폴링의 전체 파일 조회 축소 | 중간 | 1~3번 병합 후 기준값 측정 |

비용은 구현과 회귀 검증 범위에 대한 상대 추정이다. 아래 재현 수치는 이전 분석에서 테스트 대역으로 관찰한 값이다. 이번 검토에서는 `033a8ee`의 소스로 저장 예외, 재시작 복구, 종료 코드 판정 순서를 확인했다. 추가 회귀 테스트와 5번의 성능 측정은 각 PR에서 수행한다.

## 1. 시작 후 저장되지 않은 tmux 세션 회수

**근거.** 러너는 세션을 생성한 뒤 작업이 여전히 `running`일 때 세션 정보를 저장한다. 그 사이 취소가 완료되면 저장이 거절되지만 러너는 그 결과를 확인하지 않는다. 분석에서는 API가 `cancelled`를 반환한 뒤 세션 생성이 끝났고, 세션 종료 호출은 0회였다. [세션 시작과 저장](../src/jobs/job-runner.service.ts#L414) · [API 취소](../src/jobs/jobs.service.ts#L176)

세션 생성이 성공한 직후 저장에서 예외가 발생하는 경로도 있다. 두 호출이 같은 `try` 안에 있어 현재는 생성된 세션을 회수하지 않고 `markRunningJobFailed()`로 넘어간다. [저장 예외 처리](../src/jobs/job-runner.service.ts#L423) · [실패 기록과 알림](../src/jobs/job-runner.service.ts#L480)

**영속 복구 계약.** 기존 orphan 정리는 저장된 작업 ID를 모두 건너뛴다. 따라서 취소 결과가 남아 있는 작업도 회수 대상을 찾을 수 있도록, 다음 절차를 세션 시작·기동 복구 양쪽에 적용한다. [기존 정리의 제외 조건](../src/jobs/tmux-session-runner.service.ts#L369)

1. `tmux new-session` 호출 전에 작업별 비공개 세션 디렉터리에 `cleanup-pending.json`을 원자적으로 기록한다. 내용은 작업 ID와 그 ID에서 생성한 정확한 세션 이름이다. 기록이 실패하면 세션을 시작하지 않는다. 새 파일을 기존 아티팩트 허용 목록에 포함하고, 보존 기간 정리가 미해결 기록을 지우지 않도록 한다. [세션 생성 순서](../src/jobs/tmux-session-runner.service.ts#L127) · [아티팩트 허용 목록](../src/jobs/tmux-session-runner.service.ts#L89)
2. 작업에 세션 정보가 저장되면 기록을 해제한다. 조건부 저장이 거절되거나 예외가 나면 기록을 유지한 채 해당 세션을 회수한다. 종료 실패 또는 생존 여부가 불명확하면 다음 폴링에서 재시도한다. 종료 성공이나 세션 부재가 확인된 뒤, 아직 `running`인 미연결 작업의 실패 전이까지 마치면 기록을 해제한다. 이미 취소나 완료 콜백이 결과를 기록한 작업은 세션만 회수한다.
3. 재기동 시 인스턴스 잠금을 얻고 저장소를 준비한 직후, 중단 작업 복구와 보존 기간 정리보다 먼저 디스크의 미해결 기록을 읽는다. 작업 ID와 세션 이름을 대조하고, 작업에 같은 세션이 정상 저장돼 있으면 기록만 해제한다. 이는 저장 성공 직후 기록을 지우기 전에 중단된 경우다. 세션이 연결되지 않은 작업은 최종 상태인 경우에도 2번의 회수를 재개한다. 작업 조회 오류나 이름 불일치는 기록을 보존하고 진단을 남긴다. 회수 대기 중인 작업은 일반 복구가 먼저 실패 처리하지 않도록 한다. [기동 순서](../src/jobs/job-runner.service.ts#L36) · [세션 이름과 부재 판정](../src/jobs/tmux-session-runner.service.ts#L337)

**완료 기준**

- 취소 또는 완료 콜백이 먼저 최종 상태를 기록하도록 시작 반환을 지연시킨다. 시작을 재개하면 먼저 기록한 상태가 보존되고, 살아 있는 fake tmux 세션은 0개, 완료 알림은 1회여야 한다. [상태 전이 경합 테스트](../test/unit/job-transition-race.spec.ts)
- fake tmux의 세션 생성을 성공시킨 뒤 세션 정보를 붙이는 저장 호출에만 예외를 한 번 주입한다. 후속 저장은 성공하도록 두고, 다음 폴링까지 실행해 최종 상태 `failed`, `execution.errorType=execution_error`, 살아 있는 세션 0개, 해당 작업의 완료 알림 1회를 확인한다. 회수 명령도 한 번 실패하는 변형에서는 재시도 후 같은 결과여야 한다. 정상 시작 시에는 회수 명령이 0회여야 한다. [러너 테스트](../test/unit/job-runner.service.spec.ts)
- **종료 실패 → 재시작 → 기동 중 회수.** 취소 또는 완료 콜백이 이긴 작업의 결과와 알림 이력을 디스크에 저장하고 첫 종료 명령을 실패시킨다. 세션 생존과 미해결 기록을 확인하고, 다음 재시도 전에 첫 러너를 중단한다. 같은 파일 저장소와 살아 있는 fake tmux 세션을 사용해 새 러너를 기동한다. 이전 러너의 메모리 없이 종료에 성공해야 한다. 살아 있는 세션과 미해결 기록은 각각 0개, 작업의 최종 상태·출력·종료 코드·`notifyOutcome`·`notifyHistory`는 재시작 직전과 같고 추가 완료 알림은 0회여야 한다. 한 번 더 기동해 추가 종료 호출과 알림도 각각 0회인지 확인한다. [기동 시 알림 복구](../src/jobs/job-runner.service.ts#L200)
- 정상적으로 연결된 실행 중 세션에 미해결 기록만 남긴 채 재기동한다. 기록만 해제되고 세션은 살아 있어야 한다. 이 사례와 첫 종료 실패 사례를 함께 통과해야 PR 1을 병합한다.

## 2. tmux 결과 수집 오류를 작업 단위로 격리

**근거.** `runOnce()`는 실행 중인 tmux 작업을 수집한 뒤 대기 작업을 선택한다. A의 결과 파일 읽기만 실패하게 했을 때 동시성 한도 2에 빈 슬롯이 있었지만, 두 번의 폴링에서 대기 작업 B의 시작 시도는 0회였다. [폴링 순서](../src/jobs/job-runner.service.ts#L224) · [수집 루프](../src/jobs/job-runner.service.ts#L445)

브리지 기동 때도 같은 문제가 발생할 수 있다. `onModuleInit()`은 `recoverInterruptedJobs()`가 끝난 뒤에 폴링을 등록한다. 이 복구 루프에서 A의 수집 예외가 전파되면 첫 폴링에도 도달하지 못한다. [기동 순서](../src/jobs/job-runner.service.ts#L36) · [재시작 복구 루프](../src/jobs/job-runner.service.ts#L120)

**구현.** 재시작 복구와 주기 폴링 양쪽에서 개별 tmux 작업의 수집 오류에 작업 ID를 기록하고 다음 작업으로 진행한다. 복구 중 수집에 실패한 A는 중단 작업을 `failed`로 바꾸는 분기를 건너뛴다. A는 `running`으로 남아 슬롯 하나를 점유하며 다음 주기에 다시 수집된다. 실행 목록 자체의 조회 실패는 해당 기동 또는 폴링의 오류로 전달한다.

**완료 기준**

- 주기 폴링에서 A의 수집만 실패시킨다. 동시성 한도 2에서 같은 폴링에 B가 한 번 시작되고, 한도 1에서는 A가 실행 중인 동안 B가 대기해야 한다.
- 재시작 테스트는 디스크에 저장된 상태를 본떠 tmux 세션이 있는 `running` A와 `queued` B로 시작한다. A의 결과 읽기 오류를 첫 폴링까지 유지한 채 `onModuleInit()`이 성공하고 한도 2에서 B가 정확히 한 번 시작되는지 확인한다. 그 시점에 A는 `running`이고 완료 알림은 0회여야 한다. 오류를 해제한 다음 폴링에서 A의 결과와 알림이 각각 한 번 확정돼야 한다. 전체 목록 조회 실패에 대한 기존 테스트도 통과해야 한다. [러너 테스트](../test/unit/job-runner.service.spec.ts)

## 3. 시간 초과 시 실제 세션 종료 확인

**근거.** 시간 초과 분기는 `kill-session`의 반환 코드를 확인하지 않고 작업 실패 결과를 만든다. 같은 서비스의 아티팩트 정리 경로에는 세션 부재와 tmux 조회 오류를 구별하는 판정이 있다. [시간 초과 처리](../src/jobs/tmux-session-runner.service.ts#L218) · [세션 존재 확인](../src/jobs/tmux-session-runner.service.ts#L341)

**결과 판정.** 종료 시도가 실패해 작업이 아직 `running`이면, 다음 폴링에서 발견한 종료 코드를 우선한다. 따라서 재시도 전에 `exitCode=0`이 기록되고 출력 수집도 정상이면 `succeeded`로 확정한다. 러너가 시간 초과를 관찰했다는 사실만으로 작업이 강제 종료됐다고 단정할 수 없고, 종료 코드 우선은 재시작 뒤에도 현재 파일에서 같은 결과를 판정할 수 있다. [종료 코드와 수집 오류 판정](../src/jobs/tmux-session-runner.service.ts#L182)

**구현.** 종료 코드가 없고 시간 초과에 도달하면 종료를 시도한다. 종료 성공 또는 세션 부재가 확인되면 기존 timeout 결과를 기록한다. 종료 명령이 실패하고 세션이 살아 있거나 존재 여부가 불명확하면 `running`을 유지한다. 다음 폴링도 종료 코드 확인부터 시작한다.

**완료 기준.** fake tmux로 ① 종료 성공, ② 세션 부재 확인, ③ 세션 생존, ④ 조회 오류를 구분한다. ①·②는 timeout으로 한 번만 완료한다. ③·④는 슬롯을 유지하고 완료 알림을 보내지 않는다. 다음 주기에 종료가 성공하면 슬롯을 반환하고 알림을 한 번 보낸다. [tmux 단위 테스트](../test/unit/tmux-session-runner.service.spec.ts) · [런타임 timeout 스모크](../scripts/runtime-smoke.js#L2323)

별도 회귀 테스트에서 첫 종료 명령을 실패시키고 세션 생존을 확인한 뒤, 다음 폴링 직전에 종료 코드 파일에 `0`을 기록한다. 출력 수집이 정상이면 최종 상태는 `succeeded`, 종료 코드는 `0`, `timedOut`은 미설정 또는 `false`여야 한다. 두 번째 종료 명령은 0회, 전체 완료 알림은 1회여야 한다. [러너의 결과 저장과 알림](../src/jobs/job-runner.service.ts#L465)

## 4. Dispatch 대기에서 저장된 완료 알림 먼저 조회

**근거.** `waitForJobCompletion()`은 반복문 진입 전에 브리지 GET을 수행한다. 완료 알림이 저장돼 있어도 브리지가 오프라인이면 알림을 한 번도 읽지 못한다. 알림이 없으면 첫 반복에서 GET이 두 번 발생한다. 기존 테스트도 알림 적중 시 GET 1회를 기대한다. [대기 로직](../omx-dispatch/job-operations.ts#L161) · [기존 테스트](../omx-dispatch/job-operations.test.ts#L245)

**구현.** 반복문 앞의 GET을 제거하고, 각 반복에서 대상 작업의 알림을 먼저 조회한다. 알림이 없을 때만 GET으로 상태를 읽는다. 기존 대기 기한, 종료 상태를 관찰한 뒤 알림을 기다리는 유예 시간, `notificationMissing` 응답 형식을 유지한다.

**완료 기준.** 브리지 호출이 실패하도록 설정해도 저장된 대상 알림이 있으면 GET 0회로 완료 결과를 반환한다. 다른 작업의 알림은 이후 조회할 수 있어야 한다. 대상 알림이 없으면 첫 반복의 GET은 1회이며, 기존 유예 시간 만료·실행 중 대기 만료·브리지 오류도 각각 검증한다. [Dispatch 테스트](../omx-dispatch/job-operations.test.ts) · [작업별 알림 조회](../omx-dispatch/notification-store.ts#L149)

## 5. 유휴 폴링 비용을 측정한 뒤 전체 조회 축소

**근거.** 기본 동시성 2에서 유휴 폴링 한 번이 `listAll()`을 3회 호출했다. 한 번의 조회는 보관된 작업 JSON 전체를 읽고 정렬한다. 기본 폴링 간격은 500ms이고 완료 작업 보관 개수 기본값은 1,000건이다. [폴링과 작업 선택](../src/jobs/job-runner.service.ts#L281) · [저장소 조회](../src/jobs/job-queue.repository.ts#L113) · [기본 설정](../src/config/bridge-config.ts#L298)

**측정 전 결정 기준.** 기본 폴링 간격 500ms의 5%인 **25ms**를 유휴 폴링 1회의 소요 시간 예산으로, 10%인 **50ms**를 보관량 증가로 허용할 제출→실행 시작 지연 증가분으로 정한다. 두 값은 이번 최적화의 착수 판단용 제안값이다. 완료 작업 1,000건에서 유휴 폴링 p95가 **25ms 이하**이고, 제출→실행 시작 p95가 0건 대비 **50ms 이하로 증가**하면 측정 결과를 남기고 종료한다. 어느 하나라도 초과하면 최적화에 착수한다. 경계값과 같은 경우는 예산 이내로 본다.

**측정 방법.** 같은 장비, Node 버전, 동시성 2, 폴링 간격 500ms에서 임시 저장소의 완료 작업 0건과 1,000건을 비교한다. 초기화와 정리가 끝난 뒤 각 조건에서 유휴 폴링 100회의 전체 조회 수, 작업 파일 읽기 수, 폴링 시작부터 해당 주기의 조회 완료까지 걸린 시간을 기록한다. 제출 지연은 별도 실험에서 조건마다 같은 fake 작업을 한 번에 하나씩 100회 제출해 측정하고, 표본마다 기준 보관 건수를 복원한다. 각 100개 표본을 오름차순 정렬한 95번째 값을 p95로 사용한다. PR에 두 조건의 원시 호출 횟수와 p95, 지연 차이, 착수 여부를 함께 기록한다.

**개선 후 병합 기준.** 기본 동시성에서 유휴 폴링당 전체 조회가 3회에서 1회 이하로 줄고 완료 작업 1,000건에서 파일 읽기 수도 감소해야 한다. 제출 지연은 같은 보관 건수에서 구현 전후를 비교한다. 0건과 1,000건 **각각** `변경 후 제출→실행 시작 p95 − 변경 전 p95 ≤ 50ms`여야 한다. 정확히 50ms면 통과하고 어느 한 조건이라도 초과하면 병합을 보류한다. PR에 각 조건의 변경 전후 p95와 차이를 ms 단위로 기록한다. FIFO 순서, 중복 실행 방지, 외부 tmux 작업을 포함한 동시성 상한, 제출 직후 러너를 깨우는 경로도 모두 통과해야 한다. ## 구현 PR 검증과 인계

1. 최신 `develop`에서 해당 항목의 기존 동작을 회귀 테스트나 기준 측정으로 먼저 확인한다. 단계별로 브랜치를 분리해 개별 병합과 되돌리기가 가능하게 한다.
2. 1~3번과 5번은 관련 Jest 테스트를 `npm test -- --runTestsByPath <테스트 파일>`로 실행한다. 4번은 `npm --prefix omx-dispatch test`로 확인한다.
3. 동작을 변경한 PR은 대상 테스트 통과 후 `npm run verify`, `npm run verify:runtime` 순서로 검증한다. PR에는 재현 조건, 수정 전후 관찰값, 스모크 결과를 기록한다. 5번이 측정으로 끝나면 측정 환경과 판단 근거가 산출물이다. [저장소 검증 절차](release-verification.md)
