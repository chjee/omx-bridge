# 유휴 폴링 전체 조회 측정 결과

기준 커밋 `464d0bc`에서 완료 작업 1,000건의 유휴 p95는 309.89ms였고, 0건 대비 제출 p95 증가분은 430.36ms였다. 착수 예산은 각각 25ms와 50ms다. 후보 커밋 `765dd5a`의 성능 병합 기준은 **충족**이다.

## 실측값

조회·읽기는 각 조건 100개 표본의 합계다. p95의 단위는 ms다. 제출 시에는 백엔드 진입 순간 두 카운터를 함께 기록한다. 진행 중인 전체 조회는 그 시점까지 발행한 파일 읽기만 집계된다. 차이는 반올림 전 p95로 계산했다.

| 보관 작업 | 측정 | 변경 전 전체 조회 | 변경 후 전체 조회 | 변경 전 JSON 읽기 | 변경 후 JSON 읽기 | 변경 전 p95 | 변경 후 p95 | p95 차이 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 0 | 유휴 tick | 300 | 100 | 0 | 0 | 1.27 | 0.67 | -0.60 |
| 0 | 제출→실행 | 400 | 400 | 500 | 500 | 5.94 | 12.15 | +6.20 |
| 1,000 | 유휴 tick | 300 | 100 | 300,000 | 100,000 | 309.89 | 117.65 | -192.24 |
| 1,000 | 제출→실행 | 472 | 400 | 385,485 | 306,406 | 436.30 | 307.33 | -128.97 |

제출 중 다음 예약 tick과 겹친 표본은 0건에서 0→0개, 1,000건에서 100→0개였다. 제출은 유휴 tick이 끝난 직후 시작하므로, 이 값은 타이머와 겹친 I/O를 포함한 지연이다. [표본별 원자료](runner-poll-samples.csv)

## 병합 판단

- 보관량별 유휴 tick 최대 조회 횟수는 0건에서 1회, 1,000건에서 1회다. 허용 상한은 1회다.
- 완료 작업 1,000건의 tick당 평균 파일 읽기는 3,000회에서 1,000회로 바뀌었다.
- 같은 보관량의 변경 전후 제출 p95 차이는 0건 +6.20ms, 1,000건 -128.97ms다. 각각의 병합 상한은 +50ms다.
- 변경 후에도 보관 작업 1,000건의 유휴 p95는 117.65ms이고 0건 대비 제출 p95 증가분은 295.19ms다. 남은 비용에는 보관 파일을 읽고 정렬하는 전체 조회가 포함된다.
- 경합 테스트에서 오래된 빈 큐 조회가 진행 중일 때 두 작업을 동시에 제출했다. 외부 tmux가 슬롯 하나를 점유한 상태에서 첫 작업만 즉시 시작했고, 슬롯 반환 뒤 두 번째 작업이 시작됐다. 실행 순서는 FIFO였고 작업별 실행은 각 1회였다.

빈 큐를 관찰한 사실만 한 tick의 슬롯끼리 공유한다. 새 제출은 별도 tick을 깨운다. 작업을 선점할 때는 claim 잠금 안에서 현재 저장 상태와 tmux 점유를 읽고 조건부 상태 전이를 수행한다.

## 측정 조건

기준 소스는 `464d0bcd9f6fb37c53ee29494264619271dce7b4`다. 같은 WSL2 호스트(Intel Core Ultra 7 155H, Linux 6.18.58.1, Node v24.14.1)의 `/tmp` ext4에서 두 빌드를 순차 실행했다. 동시성 2, 실제 폴링 간격 500ms, 기본 libuv 스레드풀을 사용했다. 보관 작업은 파일당 1,508바이트인 성공 결과로, 1,024자 stdout과 기록된 알림 결과를 포함한다. 페이지 캐시를 강제로 비우지 않았다.

보관량·실험별로 새 임시 디렉터리와 러너를 사용한다. 초기화, 중단 작업 복구, 최초 정리, 알림 복구, 첫 즉시 tick을 마친 뒤 측정한다. 실제 파일 저장소와 제출·실행 스케줄러를 사용하고 OMX 실행과 알림 전송은 테스트 대역으로 대체한다.

- **유휴 tick**은 500ms 타이머가 `tick()`에 진입할 때부터 그 호출이 시작한 모든 `runOnce()` Promise가 끝날 때까지다. 해당 tick의 비동기 문맥에서 실제 `listAll()`과 작업 디렉터리 바로 아래 UUID JSON에 대한 `fs.promises.readFile()` 호출을 센다. 파일 읽기 횟수는 OS 페이지 캐시 적중도 포함한다.
- **제출 지연**은 별도 실험에서 매번 예약된 유휴 tick이 끝난 직후, 동일한 새 Dispatch 작업을 `JobsService.createJob()`으로 제출하기 직전부터 fake 실행 백엔드 진입까지다. 요청 ID 재사용은 없다. 타이머는 정상 작동하며 측정 창에 시작된 조회·읽기를 집계한다. 느린 제출 도중 추가 타이머가 실행된 횟수는 원자료의 `overlappingTimers`로 구별할 수 있다.
- 한 작업과 후속 tick이 끝나면 terminal 상태를 확인하고 그 작업 파일만 삭제한다. 다음 표본은 기준 보관 건수를 다시 확인한 뒤 시작한다. 초기화, 복원, 백엔드 진입 이후의 작업은 지연에서 제외한다. p95는 각 조건의 100개 소요 시간을 오름차순으로 정렬한 **95번째** 값이다.

## 재현 명령

PR 결과가 포함된 저장소 루트에서 실행한다. 각 체크아웃을 빌드한 다음 동일한 측정 스크립트를 사용한다. 두 실행은 같은 장비·임시 파일시스템에서 순차 실행한다.

```bash
git worktree add --detach ../omx-bridge-pr5-base 464d0bcd9f6fb37c53ee29494264619271dce7b4
cp scripts/benchmark-runner-poll.cjs ../omx-bridge-pr5-base/scripts/
(
  cd ../omx-bridge-pr5-base &&
  npm ci && npm run build &&
  BENCH_SAMPLES=100 node scripts/benchmark-runner-poll.cjs > /tmp/bridge-pr5-before.json
)
npm ci && npm run build
BENCH_SAMPLES=100 node scripts/benchmark-runner-poll.cjs > /tmp/bridge-pr5-after.json
```

결과 JSON에는 Node·커널·CPU·파일시스템, 측정 스크립트와 빌드된 러너의 SHA-256, 각 표본의 소요 시간과 카운터가 들어간다. 호스트 부하와 파일 크기가 달라지면 밀리초 수치도 달라질 수 있다.

측정 도구 SHA-256은 `85ee38038f430508cf2d61b22fcc6360f26741c7b16eb58e8d124c900c84c2d0`이다. 빌드된 러너의 SHA-256은 기준 `3bf93b328a5013b285ab757d37d28c0bf85b4179ecf156557cd79f000c3e3066`, 후보 `69f74be25ae40f56cf91d7e3567ff6850d6a7efc726fa6e3190bb1302ce17049`이다.
