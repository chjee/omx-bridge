# omx-bridge 개선 실행계획

기준은 `develop`의 `2762be3`이다. 우선순위는 서비스 가용성, 클라이언트 대기 시간 보장, 제출 비용, 알림 이력 정확성 순이다. 각 단계는 독립 브랜치에서 테스트와 구현을 함께 검토하고 개별적으로 병합하거나 되돌릴 수 있다.

## 1. 주기 실행 실패 후 러너 복구

- 변경 지점은 `src/jobs/job-runner.service.ts:46`의 주기 정리 콜백과 같은 파일 281행의 `runOnce()` 호출이다. 두 백그라운드 호출에서 거부된 Promise를 처리하고 실패한 작업 종류와 오류를 기록한다. 다음 예약 주기에 재시도한다.
- 폴링 복구 테스트는 `test/unit/job-runner.service.spec.ts`에서 `maxConcurrency = 1`과 가짜 타이머를 사용한다. 빈 큐에서 초기 조회와 즉시 실행되는 첫 `tick()`을 마친 뒤, 러너를 깨우지 않고 대기 작업 한 건을 저장한다. 첫 예약 폴링의 조회만 실패시킨다. 경고가 기록되고 다음 주기 직전까지 실행 횟수가 0인지 확인한다. 타이머를 다음 폴링까지 진행한 뒤 같은 작업의 실행 횟수가 정확히 1인지 확인한다.
- 주기 정리는 별도 테스트에서 첫 예약 호출을 실패시키고 다음 예약 호출이 성공하는지 확인한다. 두 타이머 테스트 모두 처리되지 않은 Promise 거부 없이 끝나야 한다.
- 오류 처리는 백그라운드 호출 지점에 둔다. 정상 운영 중 `runOnce()`와 `cleanupTerminalJobs()`를 직접 호출해 같은 저장소 오류를 주입하면 각각 원래 오류로 reject되어야 한다. `onModuleInit()`이 기다리는 최초 정리 실패도 초기화 호출자에게 전달되어야 한다.

## 2. 클라이언트 타임아웃에 응답 본문 읽기 포함

- `omx-dispatch/bridge-client.ts:33` 및 `omx-bridge-plugin/index.ts:325`에서 요청 시작부터 `response.text()` 완료까지 하나의 타이머와 중단 신호를 유지한다. 두 패키지가 사용하는 기존 타임아웃 메시지와 HTTP 오류 상세 형식을 보존한다.
- `omx-dispatch/bridge-client.test.ts`와 `omx-bridge-plugin/test/index.test.ts`에서 헤더를 즉시 반환하고 본문 읽기만 중단 신호까지 대기시키는 테스트를 추가한다. 각 클라이언트의 공개 호출 경로를 사용한다.
- 완료 기준은 본문 대기 중 신호가 중단되고 기존 타임아웃 오류가 반환되는 것이다. 성공 JSON과 HTTP 오류 본문 처리도 통과해야 한다. 가짜 타이머 또는 제어 가능한 응답으로 경과 시간의 오차에 의존하지 않는다.

## 3. 작업 생성 중 저장소 전체 조회를 한 번으로 제한

- `src/jobs/jobs.service.ts:34`의 생성 잠금 안에서 목록을 한 번 조회해 `source + requestId` 중복 판정과 활성 작업 수 계산에 사용한다. 현재 중복 검색은 같은 파일 258행, 활성 집계는 `src/jobs/job-queue.repository.ts:156`에 있다. 재사용 범위는 제출 한 건이다.
- 중복 조회와 fingerprint 검증을 용량 검사보다 먼저 수행한다. 활성 상태는 기존과 같이 `queued`와 `running`이다.
- `test/unit/jobs.service.spec.ts:94`의 테스트 대역은 `countActive()`에서 메모리의 Map을 직접 읽는다. 실제 저장소는 같은 메서드 안에서 `listAll()`을 다시 호출한다. 러너 트리거를 격리하고 새 `requestId`로 한 건을 제출한 뒤, **`repository.listAll()` 호출 1회와 `repository.countActive()` 호출 0회**를 함께 검사한다. 기존 구현은 두 번째 단언에서 실패해야 한다.
- 큐가 가득 찼을 때 동일 요청은 기존 ID, 충돌 요청은 409, 신규 요청은 429여야 한다. 동시 동일 요청은 한 건만 저장하고 기존 레거시 fingerprint 테스트도 통과해야 한다.
- 성과 지표는 신규 requestId 제출의 전체 조회 **2회 → 1회**다. 운영 지연 감소율은 별도 측정 대상이다.

## 4. 최근 10건 보관과 알림 시도 번호 증가를 분리

- 작업별 저장 잠금 안에서 최신 `notifyHistory`를 읽는다. 보관된 `attemptIndex` 중 유효한 비음수 안전 정수의 최댓값에 1을 더한다. 최댓값이 `Number.MAX_SAFE_INTEGER`이면 현재 이력에 없는 가장 작은 비음수 정수를 사용한다. 유효한 번호가 하나도 없으면 현재 이력 길이를 사용하며, 빈 이력의 첫 번호는 0이다. 최근 10건의 기록 순서는 배열 순서를 따르고 최신 결과는 `notifyOutcome`에 저장한다.
- `test/unit/job-notify.service.spec.ts:143`에서 12회 기록 후 보관된 번호가 2부터 11이고 최신 결과가 11인지 확인한다. 혼합 이력 예시로 `[10, 10, 번호 없음, -1, 1.5, 2 ** 53, 3]`의 다음 번호는 11, 유효 번호가 없는 `[번호 없음, -1]`의 다음 번호는 2여야 한다. 같은 작업의 자동·수동 기록이 겹칠 때도 두 결과에 서로 다른 유효 번호가 하나씩 부여되어야 한다.

## 병합 및 검증

구현 전에는 이 계획과 문서 목록(`docs/README.md`)을 하나의 문서 전용 커밋으로 정리한다. `git status --short --branch`에서 `develop`의 변경 파일과 미추적 파일이 없는지 확인한 뒤 첫 구현 브랜치를 만든다.

각 단계는 최신의 깨끗한 `develop`에서 시작한다. 해당 회귀 테스트로 기존 문제를 확인한 뒤 수정하고, 대상 테스트 → `npm run verify` → `npm run verify:runtime` 순서로 검증한다. 신규 diff와 작업 트리를 검토한 뒤 단계별 Lore 커밋으로 병합한다. 위 검증은 구현 단계의 완료 조건이다.
